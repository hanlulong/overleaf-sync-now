# Troubleshooting

| Symptom | Fix |
|---|---|
| `No valid Overleaf cookies` | Cookies expired or never set. **The hook blocks AI writes (exit 2)** so the AI re-auths rather than editing a stale copy; reads get a warning. Run `overleaf-sync-now login` yourself in a terminal (works on Chrome 127+ Windows); `doctor` shows which auth source failed. Headless fallback: run `overleaf-sync-now save-cookie` and paste the cookie at its hidden prompt. Never paste the cookie into the AI chat. `setup` won't help in non-interactive/agent context — it only retries auto-detect. |
| `login` shows *"This browser or app may not be secure"* (Google sign-in) | Google's anti-automation gate is rejecting the managed browser. Bypass it by setting an Overleaf-specific password at https://www.overleaf.com/user/password/reset, then re-run `overleaf-sync-now login` and use email+password (Google never sees that flow). See [authentication → Google block](authentication.md#what-if-google-blocks-the-sign-in). |
| `[overleaf-sync-now] Overleaf rejected /updates (HTTP 401)` / `... (HTTP 403)` (edit blocked) | The cached session was revoked or expired mid-use. Same fix as above; after `login`, retry the edit. |
| `Could not tell which Overleaf project <folder> belongs to: not logged in to Overleaf` (edit blocked) | First use of a folder before auth was captured. Run `overleaf-sync-now login`, then retry. |
| `Could not tell which Overleaf project ...: N living Overleaf projects are named ...` (edit blocked) | Two or more active projects share the folder name. Pick the right id from the list and run the printed `overleaf-sync-now link <project_id> "<folder>"`. |
| `Could not tell which Overleaf project ...: no living ... Overleaf project is named ...` (edit blocked) | The folder name doesn't match any active project (renamed on Overleaf, trashed, or a different account). Get the id from the project URL and run `overleaf-sync-now link <project_id> "<folder>"`. A folder under `Apps/Overleaf/` that isn't an Overleaf project: create an empty `.overleaf-sync-ignore` file in it, or list it in `OVERLEAF_SYNC_IGNORE` (folders separated by `:` on macOS/Linux, `;` on Windows). Note that Overleaf imports a new folder created there as a new project, and the `.overleaf-sync-ignore` file syncs into it like any other file. So the file only takes effect while the folder is not linked and its name matches no project; it can never switch protection off for a real (or shared) project. To opt out a real project on your machine, use `OVERLEAF_SYNC_IGNORE`. |
| `... the folder looks like a numbered duplicate of '<name>'` (edit blocked) | Overleaf's Dropbox sync may append a number to the folders of projects that share a name (`Paper (1)`, `Paper 2`). The tool won't guess which project such a folder is; pick the id from the list and run the printed `link` command. |
| `Refreshed from Overleaf: newer web edits were just pulled into <file>` (edit blocked) | Working as intended (since 0.5.0): the file changed on the web after the agent last saw it. The agent re-reads the file and redoes the edit. |
| `Conflict: <file> changed on Overleaf, and was also saved locally in the last 30 s` (edit blocked) | Both sides edited the file within seconds. The message lists the steps: run the printed `overleaf-sync-now sync --wait "<folder>"` (it waits until the local save is 30 s old, then pulls; the local copy is backed up first), re-read the file, check that both changes are there, then retry. A retry before that is blocked again. If it repeats, someone is editing the file on overleaf.com right now. Every earlier version is in the project's History on overleaf.com. |
| `<file> was renamed on Overleaf to <new>` / `<file> was deleted on Overleaf` (edit blocked) | The web side renamed or deleted the file; the local copy is outdated. Edit `<new>` instead, or delete the outdated local copy once you're sure (the hook allows `rm`, `git rm`, `Remove-Item` or a patch `*** Delete File:` on that path). The tool never deletes local files itself. |
| `Could not reach Overleaf: this command runs in a sandbox that blocks network access ...` | Codex CLI's default sandbox has no network access (it sets `CODEX_SANDBOX_NETWORK_DISABLED=1`; on macOS, DNS and connections fail inside it). This is **not** an auth problem: the cookie was not checked. It applies to commands the agent runs (`overleaf-sync-now sync`, `status`): approve running `overleaf-sync-now` with network access, or run it from a normal terminal. **Don't** run `setup`/`login`/`doctor` from inside the sandbox — they hit the same block. The automatic hook is not affected: Codex runs hooks outside its sandbox. |
| `Could not reach Overleaf (...). This looks like no network connection ...` | Offline, a DNS or proxy failure, or an Overleaf outage (also HTTP 429/5xx on the login check). Not an auth problem; nothing to re-log. The hook lets the call through without a refresh; run `overleaf-sync-now sync` once you're back online. |
| `status` reports `Cookie auth: UNKNOWN — could not reach Overleaf` | Same as the two rows above. `status` and `doctor` only say INVALID when Overleaf actually answered and refused the cookie; `save-cookie` saves nothing until it can check the value. |
| `[overleaf-sync-now] SKIP <file>: local modified Ns ago (< 30s protection window)` | Working as intended. The recent-mtime guard refuses to overwrite a local file you may still be editing. Run `sync --wait` (waits until the file is older than 30 s, then pulls), or `sync --force` to override now (the local copy is backed up first). Files the tool itself just wrote don't count as local saves. |
| `[overleaf-sync-now] SKIP <file>: the local file can't be read (...)` | The local file exists but can't be read (permissions), so it can't be backed up; it is not overwritten, and the next sync retries. Fix its permissions. |
| `[overleaf-sync-now] KEPT local <file>: it differs from Overleaf and was changed locally after Overleaf's last change to it ...` | A first sync (or a full comparison after a long gap) found local edits Overleaf never received — typically Dropbox was paused or offline. The local file was kept; Overleaf's version is in `<DATA_DIR>/conflicts/<project>/<timestamp>/`. Compare the two (`diff`) and keep what you want; Dropbox uploads the local file to Overleaf once it syncs again. The hook's note (shown to you and to the agent) says so, and the first agent write to that file after the pull, even one that follows a Read, is blocked once with a `Conflict: ... differs from Overleaf's copy` message so it asks you first. To take Overleaf's version instead, run `overleaf-sync-now sync --force` (the local file is backed up first). |
| Want an older local version back | Every file a refresh overwrote is in `<DATA_DIR>/backups/<project>/<timestamp>/` for 30 days. Overleaf's History panel has every version too. |
| Hook not firing in Claude Code | Restart Claude Code. Verify `~/.claude/settings.json` (or `$CLAUDE_CONFIG_DIR/settings.json`) contains our PreToolUse entry with matcher `Read\|Edit\|Write\|Bash\|PowerShell`, `"args": ["hook"]` and an absolute `command` path that exists. After upgrading, re-run `overleaf-sync-now install` so an old entry (matcher `Edit\|Write\|MultiEdit`, or a short `timeout` such as 8 s that kills a first pull) is rewritten. |
| Hook not firing in Codex CLI | Run `overleaf-sync-now install` (writes `~/.codex/hooks.json`), restart Codex, then run `/hooks` and trust the `overleaf-sync-now` entry — Codex skips new or changed hooks until you do. Check that hooks aren't disabled (`hooks = false` under `[features]` in `~/.codex/config.toml`). |
| Codex lists the `overleaf` skill twice | An old copy is still in `~/.codex/skills/overleaf/`. Re-run `overleaf-sync-now install`; it removes that copy (if it's ours) and keeps the one in `~/.agents/skills/overleaf/`. |
| Auto-link failed | Folder name doesn't match the Overleaf project name. Run `overleaf-sync-now link <project_id> ".../Apps/Overleaf/<name>"` for the project's top folder (not a subfolder) to write a marker file. |
| `auto-link: N non-trashed Overleaf projects named '<name>'. Refusing to guess.` | Two or more **active** projects in your Overleaf account share the folder name. The tool lists candidates with IDs, `lastUpdated`, and any archived flag. Pick one and run `overleaf-sync-now link <project_id> <folder>` to write the marker explicitly. *(New in 0.3.0; prevents silent wrong-project sync.)* |
| `WARN: marker at <folder> -> <id> is trashed/archived on Overleaf` | The `.overleaf-project` marker points at a project that has since been trashed or archived on Overleaf. Sync still proceeds (you explicitly linked it), but you probably want `overleaf-sync-now link <active_id> <folder>` to relink. |
| `WARN: marker at <folder> -> <id> is not in your Overleaf account` | The cached projects index doesn't contain that project ID. Likely causes: the project was deleted on Overleaf; the cookies belong to a different Overleaf account than when you linked. Run `overleaf-sync-now projects --refresh` to confirm, then re-link or re-auth. |
| `WARN: project <id> has recent Dropbox-origin updates touching files not present in <folder>` | Strong signal the link points at the wrong project entirely (typo'd manual `link`, a fork, etc.). Run `overleaf-sync-now status` and `overleaf-sync-now projects` to verify, then `overleaf-sync-now link <correct_id> <folder>` to fix. *(New in 0.3.0; the wrong-project smoke detector.)* |
| `ERROR: rate-limited (...). Try again in ~Ns.` | Overleaf returned HTTP 429. Manual `sync` exits 1 and prints the wait from `Retry-After` (default 60 s); it does not retry by itself. The hook lets calls through with a warning. |
| `uv tool upgrade` says *"Nothing to upgrade"* but you want the latest commit | See [operations → upgrading](operations.md#upgrading) — use the `--reinstall --refresh` form. |
| Codex CLI on Windows | `install` writes a `commandWindows` variant of the Codex hook, but that path is untested. If the hook doesn't fire, the skill tells the model to run `sync` before editing. |
| Shell edit wasn't refreshed first | The hook sees LaTeX paths written in the command (environment variables such as `$HOME` are expanded). Commands that build paths at run time (a variable set in the same command, `find -exec`, scripts) aren't detected; run `overleaf-sync-now sync` first. |
| HTTP 404 from sync | Project was deleted, archived, or auto-link picked the wrong project. Run `overleaf-sync-now status` to confirm project ID; re-link if wrong (`overleaf-sync-now link <id> .`). |
| Network error / timeout | Reported as `Could not reach Overleaf (...)` (see above). `sync` exits 1; the hook proceeds with a note and doesn't block. Try again. |
| macOS asks for your keychain password for "Chrome Safe Storage" (or another browser) | `install` / `setup` / `status` / `doctor`, or `sync` (which then stops trying for an hour after a failure), are looking for an existing Overleaf login in that browser. The tool has two cookie readers, so the same browser can ask twice. Allow it to use that login, or Deny and run `overleaf-sync-now login`. Avoid Always Allow. The hook never asks, and `doctor` skips the browsers when its check of the cached cookie could not reach Overleaf. See [authentication → keychain](authentication.md#the-macos-keychain-prompt). |
| `install`: `ERROR: could not find the overleaf-sync-now executable` / `... is in uv's cache` | Install the CLI with `uv tool install` (README), then run the installed `overleaf-sync-now install`. A uvx run lives in uv's cache, which uv may delete, so hooks can't point there. |
| `install`: `ERROR: nothing was installed` | Neither `~/.claude` nor `~/.codex` exists (or the `CLAUDE_CONFIG_DIR` / `CODEX_HOME` directory). Start Claude Code or Codex once, or set the variable, then re-run `install`. |
| `install` warns that the CLI's directory is not on your PATH | The hooks use the full path and work. To type the commands by name, run `uv tool update-shell` and open a new terminal. |
| `refresh could not write local files in <folder>` | A local file write failed (read-only folder, file locked by another program). Not a network or sandbox problem. Check permissions on the Dropbox folder. |
| Self-hosted Overleaf / Server Pro | Not supported. The tool hardcodes `https://www.overleaf.com`. PRs welcome to add a `--base-url` option. |
| Multiple Overleaf accounts | The cache holds one session at a time. See [operations → multiple accounts](operations.md#multiple-overleaf-accounts). |
| WSL + Claude Code on Windows | The CLI only sees its own filesystem. Claude Code on Windows (Win paths) won't find a tool installed inside WSL (Linux paths) and vice versa. Install in whichever environment runs your AI agent. |
| Cookies cache file is corrupt | Tool prints a warning and falls through the auth chain. Delete `<DATA_DIR>/cookies.json` to reset (run `overleaf-sync-now status` to see the resolved data dir — default `~/.overleaf-sync/`, legacy `~/.claude/overleaf-data/`). |

## Diagnostic commands

| Command | What it shows |
|---|---|
| `overleaf-sync-now status [folder]` | Data dir, cookie validity, linked project, last-sync time, **cached `toV`**. Distinguishes sandbox-blocked network from real auth failures. |
| `overleaf-sync-now status --quick` | Skips the chain-fallback step (only checks the cached cookie's network probe). Faster, but can't predict whether sync would still succeed via a stale-cache-then-refresh path. |
| `overleaf-sync-now doctor [folder]` | Every auth source it tried plus the exact error from each, plus a live `/updates` probe of the linked project. |
| `overleaf-sync-now projects` | Lists every Overleaf project the current session can see (name + ID). |
